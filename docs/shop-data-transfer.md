# 店铺 JSON 数据备份与迁移

店主在「店铺设置 → 数据管理」下载或导入 JSON。默认导出业务备份，用于店铺备份及 beta／正式环境迁移；也可以只复制配置。两个环境都需要新版 Worker、既有 UTC 迁移和新增的 **0031_shop_data_transfer.sql** 和 **0032_read_only_shop_export.sql**。0031 新增导入暂存及账号关联表。0032 新增锁、进度和额度元数据及店铺写入保护触发器；只清理旧版遗留导出快照，不修改或删除营业数据。

## 备份范围

| 模式 | 包含的数据 |
| --- | --- |
| 业务备份 | 所有玩家（包括没有平台身份的纯前台玩家）、前台卡片档案、平台身份、余额与流水、兑换码与兑换记录、会话、历史账单及保存的时间轴、商品订单、前台收款、完整历史计费规则／发布版本／会话版本绑定；店铺员工资料、账号关联、设备操作记录、设备事件日志、设备状态及麻将座位 |
| 仅配置 | 计费效果、资产定义、计费方案、礼物和商品；生成新的计费发布版本，不包含玩家、财务历史及员工账号关联 |
| 两者共同包含 | 店铺名称、位置、半径与封面；所有店铺 `app_settings`、入场／收银／身份绑定设置；Bot/API Token 的验证记录；设备定义、别名及设备能力（电源、HINATA IO、门锁、麻将配置与可跨密钥恢复的连接信息） |

v2／v3 业务备份支持**覆盖已有店铺**，无需创建空店铺。原有玩家、余额、账单、计费历史、归档状态、设置、员工和设备由备份整体替换；没有出现在备份中的这些记录也会移除。保留目标店铺的编号、所属店铺 ID、当前管理员和原店主。其他原有员工权限撤销，按备份重新关联。导入前请保留原店铺备份，覆盖操作不能单独撤销。

仅配置导入按同编号覆盖配置、设置、API Token 和设备，并补充新记录；保留玩家、余额、账单、旧会话绑定的历史计费版本，以及文件未包含的配置和设备。同编号设备保留二维码，不重复创建。v1 业务备份仅替换它能表达的业务数据，保留目标店铺资料、设备定义和其他旧格式不支持的设置；旧的座位和玩家短期绑定等关系会清理。

覆盖导入需要 **0036_overwrite_shop_import.sql**。迁移只新增索引和导入确认前失效触发器，不修改任何玩家、余额或账单，也不自动执行覆盖。触发器仅将已通过文件检查、待确认的本店导入标记为 `stale`；正常业务没有待确认任务时不写入版本记录。触发器通过 `(shop_id,kind,status)` 索引查找任务，支持同数量的记录内容修改，并保护转移记录时的原店和目标店。

v2／v3 恢复来源店铺的资料及设置，保留目标店铺的编号、所属店铺 ID 和当前管理员。导入完成后后台刷新店铺资料、运营开关和设置。店铺时区继续跟随恢复后的位置。若在**同一数据库**复制店铺，设备 ID／公开链接与来源冲突时生成新编号，并更新座位、会话、设备能力、操作、事件和状态中的对应引用；跨库无冲突时保留设备编号。直连机台的中继通道与设备令牌是全平台唯一的：已被其他店铺使用时，导入的副本会获得新通道且令牌作废，需在设备看板重新签发；恢复到原店铺时保持不变。恢复后直连链路状态一律记为断开，机台重连后更新。

后台导入区还可选择 **prism-neo** 来源：选择旧系统的 `pg_dump` 备份（`.sql`）或 `@prism/migration` CLI 导出的 JSON 快照后，浏览器先在本地转换成 v3 业务备份（转换规则与 `@prism/migration` 的映射一致，见 [从 prism-neo 数据迁移指引](migration-from-prism-neo.md)），再走同一条分片上传与覆盖导入流程。转换后的旧计费规则以停用状态导入，入场方案指向该停用方案；启用前须在计费设置中核对时区。

不复制平台全局的用户登录凭据、Passkey、OAuth 密钥、玩家个人卡片库、登录会话、设备扫码 Ticket、短期绑定码、请求去重与操作锁、实时活动推送 Token，也不复制全局封禁及登录审计。它们属于平台账号或短期运行状态，不属于店铺的业务备份。店铺范围中的禁用玩家、归档配置、已结账单和未结会话均包含在内。

纯前台玩家直接来自 `players` 与 `cashier_profiles`，不依赖平台身份或网页账号绑定。下载完成后界面展示来源环境、店铺、玩家／前台玩家／结账记录／设备数量；业务备份玩家数量为零时提示核对环境。beta 与正式版数据库各自独立，同名店铺也不能推断为同一个数据库或同一个店铺 ID。

## 账号和设备恢复

业务备份记录店铺账号与玩家／员工的关系，以及已验证登录身份的 `provider:subject`。导入不创建全局用户，也不安装登录密钥。账号访问店铺时按同一账号 ID 或已验证登录身份重新关联，平台绑定与原玩家必须一致；无法匹配的关系继续保存，并随下一次备份导出，可通过原外部平台身份重新绑定。跨库新建的纯 Passkey 账号没有可匹配的外部登录身份时，需要重新建立关联，不能凭昵称猜测。

设备能力的密钥（`device_capabilities.secret_json` 中的每个值）在下载时使用来源环境密钥解密，导入暂存时使用目标环境密钥重新加密，所以不同 `URL_ENCRYPTION_KEY` 不会破坏连接。文件中的连接信息可包含明文密码和控制 Token；应当像保存数据库备份一样保管。Bot/API Token 的哈希验证记录保留，原 Token 值无法从哈希还原，接入时仍需持有原值并更新环境／店铺地址。

恢复过程不发送收款、赠送余额或硬件控制指令。历史设备命令保留；待执行命令改为已过期，设备在线状态恢复为离线，随后由实际设备重新报告状态，避免旧控制指令重复执行。

跨环境迁移前停止旧环境营业，处理在用设备与未结账单；核对新环境余额、规则、历史账单、账号绑定及设备连接后再营业，避免同一会话在两个环境继续计费。

## JSON 格式、时间与金额

```json
{
  "format": "prism-shop-data",
  "version": 3,
  "scope": "business",
  "exportedAt": "2026-10-06T00:00:00.000Z",
  "source": {
    "publicId": "source-shop",
    "name": "来源店铺",
    "timeZone": "Asia/Shanghai",
    "origin": "https://beta.example.com",
    "location": { "latitude": 31.23, "longitude": 121.47, "radiusMeters": 80 }
  },
  "storage": { "timeZone": "UTC", "money": "minor-units" },
  "settings": { "...": "计费设置摘要" },
  "shopProfile": {
    "name": "来源店铺", "latitude": 31.23, "longitude": 121.47,
    "radiusMeters": 80, "heroData": null
  },
  "tables": { "...": "完整的数据表数组，包括空表" }
}
```

上述是结构示意，不能直接导入。每行省略 `shop_id`，其余字段是数据库原始列和值；`device_capabilities.secret_json` 中的密钥以明文导出。

当前导出 **v3**：设备身份在 `machines`，能力在 `device_capabilities`，历史在 `device_operations`、`device_events`、`device_state`（迁移 0037 引入）。导入仍接受 v1 与 v2 文件。v2 文件的 `machines` 带连接列（`hinata_url`、`hinata_password`、`ha_binding_json`、`ttlock_lock_id`、`coin_key`、`coin_after_swipe`、`mahjong_config_json`），并带 `device_commands`、`device_states`、`machine_connections` 三张表；导入时按迁移 0037 的同一规则转换：连接列变成能力，命令变成操作及其请求／结果事件（未完成的保持未完成，计费结果不变），电源状态变成观测值，`machine_connections` 丢弃。`account_links` 表包含账号关联资料。导入归属当前经鉴权的目标店铺，不接受文件指定任意店铺、表或列。

事件时间、UTC 规则、JSON 时间轴和金额保持存储原值。货币使用整数分；数量和百分比保持原值。历史计费版本与发布时区不再次转换。下载附件及分页中的 `payload_json`／`headerJson` 不进行展示时区转换。

新版 UI 同时支持 **v1 和 v2** 文件。v1 文件只能恢复其中已有的业务数据和设置摘要，并保留目标店铺资料，无法补回当时没有导出的设备或账号关联。

## 大文件与一致性

新版 UI 不再设置 10 MiB 文件上限或 128 KiB 单行上限。导出先原子获取店铺锁，再按现有主键／唯一键索引逐页读取（账号关联先分页标识，再组装关联内容），JSON 在浏览器组成。不往 D1 写入或复制任何导出内容；D1 仅保存少量锁、进度和月度额度元数据。数据库触发器拒绝该店铺的新增、更新和删除，包括后台、Bot、设备及后台任务；其他店铺不受影响。正在持有业务操作锁时不能开始导出。导入逐行读取文件，按约 256 KiB 或最多 1000 行上传分片；较大单行可以独占分片。分片请求必须小于 2 MiB，仍受 D1 单值／行大小、数据库容量及查询执行时间等服务限制。普通账单超过 128 KiB 可以导入，超过 D1 本身支持范围的记录会明确报错，不会截断。

浏览器下载最终 JSON Blob 仍需与文件大小相应的本地资源；不会把全部记录装进 Worker 内存。导出不需要 D1 快照空间，只有导入需要暂存空间。

普通分页以 **1 MiB JSON 记录内容／4096 条记录** 为上限，并按实际行大小调整；超过 1 MiB 的单行仍可单独返回，受 D1 本身限制。每页最多顺序读取 8 张非空表，小表合并在同一响应，已经读满的表直接跳过，不再发送探测请求。分页权限和任务查询放在一个 D1 batch 内，每次重新校验当前权限；业务锁的续租、取消和最终游标校验保持不变。普通表先按现有主键范围和原始字段字节数选出有限的候选键，再只序列化选中的行，按实际 JSON 字节数再次截断，避免行大小突然增大时批量生成大量会被丢弃的 JSON。账号关联的每个来源分支都直接应用游标、排序和 LIMIT，每次最多选 512 个账号，避免每页重新合并全部账号。

性能回归夹具为 1 万条资产流水：原 64 行分页产生 167 次分页请求，优化后为 5 次；同机 Miniflare 测试的导出阶段约从 11.6 秒降至 0.8 秒。回归测试约束请求数量和数据完整性，不使用依赖机器性能的耗时断言。这是本地对比，线上耗时仍受网络、D1 和实际记录大小影响。

导出区从统计阶段就显示状态，统计完成后显示已导出／总记录数和进度条，每个分页完成后更新。完成导出或主动取消后立即释放店铺锁；刷新、离开页面时中止分页并通过 beacon／keepalive 尝试取消，刷新／恢复同一标签页时清理其未完成任务。取消失败仍保留该任务标识供再次恢复。新开标签页会忽略从来源标签页复制的任务标识，其他标签页正在导出的任务不会因打开设置被自动取消。锁存在时后台每 5 秒重新查询实际状态，网络错误后仍继续查询，切回页面时立即查询；租约过期后提示自动消失。店主也可通过“取消导出，恢复营业”终止本店当前任务，包括升级前中断的任务和其他店主发起的任务。分页读取失败会将已取得读取权的任务标记失败并解锁；取消后的在途分页不能再提交成功或生成有效备份。

每页续租 5 分钟，断线后至多 5 分钟自动解锁，单次导出最长 2 小时。过期任务不能复活，分页游标不能倒退或跳跃，同一任务每次只允许一个分页读取，避免并发重复扫描；分页与锁校验在同一个读事务中执行，最终核对总记录数。导入成功后清理暂存数据；失败的导入任务可删除，遗留任务 24 小时过期并在下一次新建导入时清理。成功导入的结果凭据保留至任务过期，以支持网络失败后的幂等重试。

1. 选择店铺和文件后，浏览器先完整解析并校验文件：结构、表键齐全性和行数统计都在本地完成。校验不通过时不会发出任何请求，也不会消耗导入额度。
2. 本地校验通过后展示来源、各类记录数与覆盖范围；店主确认后才开始上传。在确认弹窗中取消不会发送任何数据。
3. 上传按约 256 KiB 或最多 1000 行分片；同一任务内重试不重复上传、不重复计数。分片写入幂等，传输中损坏的分片按相同编号自动重放一次。
4. 上传完成后服务端执行引用、计费配置与目标状态检查。检查不通过时保留已上传任务，重新确认不会重传文件；检查通过则在同一操作中立即应用。
5. 应用在 D1 batch 第一条语句内断言目标及任务状态。所有业务数据、设置、去重结果与暂存清理在一个事务中完成；任一步失败全部回滚，可使用同一请求编号重试。

目标状态包含设置、账务设置及店铺资料；文件检查后新增、删除或修改本店业务记录、配置、设备和关系均会阻止导入，即使记录数量不变也会失效。仅登录使用时间、API Token 使用时间和未改变设备状态的心跳时间戳刷新不使检查失效，避免正常轮询阻断确认。可以对同一上传任务重新检查，生成新指纹，不再消耗月度导入次数；旧指纹不能用于重新检查。其他店铺修改不影响本店任务。相同成功请求重试返回原结果，不重新导入，不再次变换时间或金额。

恢复业务历史时在同一事务内暂时停用自动发布／会话绑定及历史版本删除保护触发器，按外键顺序删除旧数据并插入原记录，再恢复全部触发器。历史版本更新保护、UTC 写入保护、导出锁及部署维护围栏始终保留；失败回滚同时恢复旧数据和触发器。全局登录凭据、导入导出额度和请求去重结果不重置，旧设备关联的去重凭据仅清空设备外键，保留原请求结果。

## API

仅店主或已授权平台管理员访问；普通员工、其他店铺用户及 Bot Token 不可访问。新建任务及旧版接口每用户／店铺每分钟最多 10 次；同一任务的分页、上传及文件检查仍逐次鉴权，不受该 10 次限制。

- `POST /api/v1/shops/:shopCode/data/exports`：`{scope: "business" | "configuration"}`，锁定店铺并创建只读导出任务，返回 `jobId`、原始 `headerJson`、表列表、记录数量和文件名。
- `GET .../data/exports/:jobId/page?after=0`：返回 `{rows:[{seq,table_name,payload_json}],cursor,done}`；使用返回的 `cursor` 请求下一页，直到 `done`。
- `DELETE .../data/exports/:jobId`：本店任一当前店主可取消导出并释放店铺锁，保留月度次数记录；其他店铺、普通员工、玩家不能取消。分页数据仍仅对发起人开放。
- `POST .../data/exports/:jobId/cancel`：相同取消操作，供离页 `sendBeacon` 使用，支持无请求体，幂等且校验登录、店主权限和请求来源。
- `POST .../data/imports`：提交不含 `tables` 的原始文件头，创建上传任务。
- `POST .../data/imports/:jobId/parts`：`{table,part,rows}`；`part` 从 0 连续编号。同内容重试接受，不同内容占用同编号返回 409。
- `POST .../data/imports/:jobId/preview`：`{counts:{完整表名:行数},parts:分片数量}`，返回 `canImport`、指纹、错误、警告及计数，另有 `target: {records, mode: "replace" | "merge"}` 表示目标现有记录数和替换模式。
- `POST .../data/imports/:jobId/apply`：`{fingerprint,operationId,overwrite?:boolean}`，原子恢复；非空店铺的业务备份必须显式 `overwrite:true`，否则返回 `IMPORT_OVERWRITE_REQUIRED`；已成功的相同请求直接重放结果。
- `DELETE .../data/imports/:jobId`：删除未完成的暂存任务，不能撤销已完成导入。
- `GET .../data/export?scope=business|configuration`：v2 原始 JSON 附件，适合常规直接下载；超大导出请使用分页任务，以避免单请求的 Worker 子请求预算。

旧版 `GET .../data/export?version=1`、`POST .../data/import/preview` 与 `POST .../data/import/apply` 保留兼容，仍有旧的 10 MiB／128 KiB 限制；旧整文件导入仍只允许空店铺；新版后台不使用这些整文件接口，v1 文件也走支持覆盖的分片任务。

验证覆盖纯前台注册／入场／收款后的备份、独立 D1 与不同密钥恢复、设备 ID 冲突和关联更新、超过 10 MiB 的文件与大于 128 KiB 的单行、锁店只读分页一致性及月度额度、账号关联、完整分片校验、幂等重试、失败回滚、非空店铺覆盖、同数量并发变更、跨店隔离、仅配置保护历史、权限和 v1 兼容。

## 月度额度与管理员授权

每家店铺按店铺时区的自然月，默认 **导出一次、导入一次**，两类额度独立，配置备份与业务备份共享导出额度。导出开始取得锁时扣除次数；v2 导入开始上传时扣除次数。取消、断线或后续失败不退回，避免反复中断绕过限制；同一导入任务的分片及确认重试不重复扣除。旧版 v1 下载同样取得锁并消耗导出额度；旧版整文件导入在真正应用事务中扣除，文件检查不扣除。

额度在 D1 触发器中原子检查，并发创建不能突破限制。达到额度返回 `EXPORT_MONTHLY_LIMIT` / `IMPORT_MONTHLY_LIMIT`，提示联系平台管理员；店铺业务写入被锁时返回 HTTP 423 `SHOP_EXPORT_LOCKED`。锁校验覆盖原店铺和目标店铺，不能通过修改 shop_id 移走记录。

平台管理员在账号管理页面的“店铺导入导出额度”输入公开店铺编号，查询并设置当月额外导入／导出次数（0–100）。每类总额度为 1 + 额外次数；保存是设置绝对值，重试不会重复增加。不改变已使用次数，不携带到下个月；店主和其他用户不能修改额度。beta 与正式环境分别计数。

- 店主 `GET /api/v1/shops/:shopCode/data/export-status`：当前月份、时区、导出／导入总额度、已用及剩余次数、导出锁状态及 `activeExport: {jobId, scope, expiresAt} | null`，只返回尚未过期的活动任务；查询不续租，不写入数据。
- 平台管理员 `GET /api/v1/admin/shops/:shopCode/transfer-allowance`：查询额度。
- 平台管理员 `PUT /api/v1/admin/shops/:shopCode/transfer-allowance`，JSON `{ "extra": 1, "importExtra": 0 }`：设置当月额外导出和导入次数。

0032 的部署回归测试从旧 stable 数据库开始，通过维护模式的真实迁移入口执行并重试，核对只删除旧导出暂存、保留玩家和余额，并保护新额度表不受维护期间普通请求写入。

### 前台玩家身份兼容

前台玩家可同时拥有外部平台身份及通过绑定码验证的 PRiSM 账号关联。业务备份保留 `cashier_profiles`、平台身份和账号关联，导入校验允许这些关系；跨 beta/正式版的账号仍按既有验证匹配流程重建。恢复后的档案保持现场收款模式且不能拥有余额资产。目标环境需先应用 `0033_cashier_player_identities.sql`，迁移不改历史计时或付款数据。

## 营业记录归档状态

0035 新建 `checkout_report_states`，业务备份包含归档与恢复的最后操作人、时间和状态，并保留所有原始账单。跨环境恢复后，归档账单继续从营业额中排除；仅配置备份不包含该表。引入此表以前的 v2 业务备份在缺失该表时按空表恢复，其他缺失表仍拒绝，v1 表集合保持不变。元数据在导出期间同样受写锁保护。详见 [营业记录归档](./merchant-report-archive.md)。
