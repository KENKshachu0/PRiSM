# PRiSM Next 完整重构路线图

## 重构完成目标

当 PRiSM Next 能够完全替代原有的 `prism-neo` 后端和 `plugin-prism-neo-koishi` 机器人调用流程，满足无人自助场馆的全部业务功能，并补充提供独立部署的管理后台 Web UI、单店自托管部署架构、Cloudflare 与本地部署切换支持、权限模型及插件开发规范时，即宣告本次重构工作圆满完成。

---

## 业务需求覆盖清单

### A. 玩家与身份绑定
- [x] **玩家注册**：通过员工端 create-player API 配合应用层服务完成新玩家开户。
- [x] **外部身份卡片绑定**：支持将 QQ 或 Aime 物理卡号绑定至同一玩家。提供 bot 身份自动识别及 staff 绑定 API。
- [x] **前台/后台玩家查询**：支持查看玩家资料、钱包余额总览、已持有的道具/月卡/票券以及历史消费记录。
- [x] **玩家状态管理**：支持封禁（`banned`）或禁用（`disabled`）指定玩家账号。
- [x] **玩家 Web 端 API**：完成 player session 登录与 Hono `/rpc/player/*` 端点，浏览器不再依赖共享 Player Token 或手写玩家 ID。

### B. 结算场次生命周期 (Session)
- [x] **自动限制**：物理命令控制（door/power/coin/scan）必须在玩家启动活跃结算场次后方可使用。
- [x] **多计时并存**：同一玩家可同时拥有多个平级活跃计费 session，例如标准入场计时叠加麻将或包间计时，最终按玩家统一结算。
- [x] **结账预览**：玩家在正式结账下机前，可以通过 API 或聊天客户端预览费用，不关单。
- [x] **确认结账**：确认扣除钱包余额，关闭场次会话。
- [x] **后台特权覆盖**：员工结账特权改单，以特权费用结算，价差部分以 `staff.override` 存入账单调整项目作为审计。
- [x] **账单与流水持久化**：使用 SQLite/D1 仓储存储结算概要。
- [x] **账单细项分离**：费用细项（时间计费、固定收费）与打折调整明细独立建表存储。

### C. 资产账本流水体系
- [x] **资产定义管理**：支持定义货币、免费货币、限时通行证（月卡）、票券、成就、称号及特权标识（由后台 save/list API 支撑）。
- [x] **资产分发与调整**：支持批量发放、增加、扣减和手动撤销玩家名下持有的资产。
- [x] **审计流水**：任何资产授予或扣减均产生追加式的账本流水（Ledger Entry）。
- [x] **资产交易分组**：每次资产变更归属在唯一的 `asset_transactions` 分组下，使结算、CDK 兑换和人工改账均可追溯。
- [x] **货币抵扣优先级**：强制保证先扣减免费余额（`free`），不足时再扣减充值余额（`paid`）。
- [x] **时效性区间控制**：仅激活且未过期的资产才能参与结账抵扣，到期或未激活的余额忽略，但在个人面板中依然可以查阅过期限制。
- [x] **合并策略**：支持合并时直接累加（`stack`）、顺延截止日期（`extend-time`）或直接覆盖（`replace`）。

### D. 礼物兑换系统 (Redeem System)
- [x] **礼物配置**：支持配置包含多项资产的礼物。
- [x] **CDK 兑换码生成**：员工端生成或批量导出带时限的 CDK 兑换码。
- [x] **规则验证**：自动校验 CDK 的时限、使用次数限制（`maxUseCount`）以及玩家单人仅可兑换一次礼物的限制。
- [x] **多渠道兑换**：玩家通过 Bot 输入命令或通过玩家端接口完成 CDK 礼物兑换。
- [x] **新玩家注册礼物**：员工在创建玩家时，可选择直接挂载并在注册完成时发放初始化礼物。

### E. 计费结算与插件化扩展
- [x] **计时费用计算**：复刻旧系统的优先级计费、工作日规则、特定日期、跨天区间（开始日锚定）、舍入分段、宽限期和最高封顶价。
- [x] **封顶记忆**：保留同一计费区间内跨场次的历史付额记忆，防止一日内重复结算导致玩家被收取的计时费用超过设定的 Cap。
- [x] **卡券打折转换**：资产定义关联启用中的 `PricingEffect` 后，结账时按其免计费、定额或比例规则生成负数调整（例如月包卡）。
- [x] **非时间计费支持**：支持代码插件挂载（如设备出币收费、赛事报名等），并实现首个可在后台创建的固定费用项目（`charge.fixed`）。
- [x] **非计时商品采购与订单**：玩家可在活跃场次内购买后台发布的赛事票、包间服务等，系统扣款生成 `BusinessItemOrder` 履约单，支持后台核销与取消。
- [x] **安全性隔离**：计费插件禁止直接触碰或修改仓储数据库，只能通过返回费用和折扣提案的方式参与结算，防止数据失控。

### F. 设备通道与局域网交互
- [x] **通道行为鉴权**：除员工手动远程调试外，玩家只能在活跃计费场次内申请 door、power 和 coin 控制。
- [x] **出币频率限制**：对单个玩家施加出币冷却（Coin Cooldown）保护，防止硬件连击或被刷币。
- [x] **物理刷卡（Aime 扫码）**：扫码指令发送后，自动校验该卡是否绑定在当前活跃会话玩家名下，并转换发送投币/刷卡动作。
- [x] **Machine WebSocket 与 ACK 机制**：游戏机器软件通过 WebSocket 接收指令，执行成功上报 `ack`；失败或超时上报 `expired` 以供员工审计。
- [x] **云端兼容性**：指令队列表设计不依赖任何云服务商特有的内存队列，基于标准 SQL 库存储以适应 CF Worker 的冷启动特征。

### G. 中文管理前台 (Staff Web)
- [x] **员工角色与鉴权**：支持 owner（所有者）、manager（店长）、viewer（员工）身份。写操作必须由 manager/owner 发起，viewer 仅支持只读，员工账号管理为 owner 特权。
- [x] **自包含客户端打包**：前台 `/admin` 完全由单页静态客户端实现，打包进 Hono 服务，无需单独部署服务器即可从任何设备访问。
- [x] **玩家与道具管理**：支持列表检索、新建玩家、查看资产持有/流水明细。
- [x] **CDK 及礼物管理**：支持创建礼物、设定礼物内道具、批量导出并作废 CDK。
- [x] **可视化计费编辑器**：在后台配置支持每日（daily）、工作日（weekday）、特定日期（specific-date）和日期范围（date-range）的时间段方案，后台提供引擎直接渲染 24 小时时间轴分段，显示营业覆盖段并向店主报告潜在的无计费空档，且支持在可视化编辑器中删除错误的草稿规则。
- [x] **业务订单核销**：列出玩家买赛事票/服务的订单，提供 fulfill/cancel 动作按钮。
- [x] **设备监控与日志**：在线监控心跳指示灯，查询近期的指令审计历史。
- [x] **基础财务报表**：指定时间段，汇总全场营业额、开单数、币数、排行榜，并支持结账流水导出为标准 CSV 格式。

### H. 机器人与机器软件适配
- [x] **Integration API 支持**：Hono 提供 Integration HTTP 接口，并支持 QQ 识别自动绑定新玩家。
- [x] **Koishi 插件**：独立仓库 `koishi-plugin-prism`（作为 `packages/koishi-plugin` 子模块）注册并实现日常快捷聊天开机/下机/扫码/充值/兑换命令。
- [x] **机器软件驱动**：游戏机软件通过 Machine WebSocket 接收投币和 Aime 指令并回传 ACK；Home Assistant 设施动作由后端适配器直接执行。旧 Agent HTTP 轮询包与路由已删除。

### I. API 规范与数据迁移
- [x] **API 分层设计**：Dashboard 和机器人调用 Hono HTTP API，机器软件使用独立的 Machine WebSocket 协议。
- [x] **CF Worker 云端组装**：在 `@prism/adapter-d1` 与运行时模块的配合下，无需更改业务代码即可在 D1/Worker 上发布。
- [x] **本地 Bun 组装**：通过 `@prism/adapter-sqlite` 实现在小主机或店长电脑上双击 Bun 即可本地运行。
- [x] **双平移数据迁移工具**：`@prism/migration` 模块包含 Postgres 和 SQLite 导出指令，可直接将旧的 postgresql pg_dump 包转换后写入新库。

### J. 金额精度纪律
- [x] **统一比较入口**：`packages/core/src/money.ts` 提供 `compareMoney` / `isPositiveQuantity` / `isZeroQuantity` / `normalizeQuantity`，替换全项目所有 `quantity > 0`、`amount === 0`、`available < amount` 这类在 `REAL` 列上不可靠的精确比较。
- [x] **算术边界量化**：结算总额、覆盖金额、折扣、分摊结果在写回前量化到分；扣减后余额收敛残渣，使已花完的持有记录能被 `diffAssetHoldings` 正确删除。
- [x] **入参量化**：定价配置、服务项目价格、计费效果金额、人工调整金额和店铺计费设置的单价/封顶在各自边界量化，超精度金额无法入库。
- [x] **回归护栏**：`money.test.ts` 加 4 处 describe 用例，含 4,000,000 组「余额够付」穷举与 90,600 组分位穷举。
- [ ] **阶段二**：引入 branded `Cents` 类型，让编译器找出剩余漏改的边界。
- [ ] **阶段三**：13 个 `REAL` 金额列迁移为 `INTEGER` 分，需停机窗口。详见 [money.md](money.md)。

## 长期遵循的研发红线 (Always-On Rules)

- **测试先行**：任何关于核心结算、资产授予和计费算法的改动，必须首先编写 TDD 测试断言。
- **Core 纯粹性**：领域层核心代码禁止直接访问网络、系统调用或持久化库，保持对运行时的零依赖。
- **端口隔离**：适配器和存储层只能实现 `storage-ports.ts` 定义的契约，严禁在数据库逻辑中夹带业务逻辑。
- **面向视图的 API 响应**：网络接口统一返回经过用例包装的视图对象，禁止向前端直接转存或回传原始数据库的整行结构。
- **插件单向提议**：第三方扩展（计费、打折、效果）仅允许提出追加计费与抵减调整的建议事实，账户扣减和账目平衡必须由核心库闭环完成。
- **金额精度纪律**：金额与资产数量的比较只能走 `packages/core/src/money.ts` 的带容差判定，禁止在 `REAL` 列的值上写 `> 0`、`=== 0` 或裸的 `<`；跨边界的金额必须量化到分。规则与例外见 [money.md](money.md)。
