# 计费时区字段审计（2026-10-05）

## 结论

新业务的规则时钟、星期、日期和计费计算统一为 UTC，调用方不需要手动填写 `timeZone: "UTC"`。写入边界负责这一约定。计费设置向导的失败已在 `bf2f55d` 修复：公共序列化器为未声明时区的新计时／封顶规则补齐 UTC，转换设置和成功响应原子提交，失败可使用原请求编号重试。

统一 UTC 后，方案和发布中的业务时区从设计上可以退役；**当前不能直接删除**。旧库升级需要原时区换算裸时钟，运行器、SQL 发布逻辑、部署保护和校验也仍读取这些字段。本次保留字段，不添加 DROP 或清除历史属性的迁移。

店铺展示时区必须保留。它来自位置，供商户 UI、规则编辑器、API 事件格式和玩家看到的店铺营业规则使用；玩家账单事件可以另外使用手机／浏览器时区。这些展示选择不参与收费计算。

## 字段与实际用途

| 字段 | 新业务中的用途 | 未统一 UTC 的旧库中的用途 | 是否可直接删除 |
| --- | --- | --- | --- |
| `pricing_configs.provider_json.timeZone` | 新计时／封顶规则写为 UTC；API 接受显式旧时区时先转换规则 | 当前方案明确声明的源时区，优先于发布／店铺设置 | 否；是 JSON 属性，不是独立 SQL 列 |
| `pricing_config_versions.provider_json.timeZone` | 历史版本通常为 UTC，运行器仍读取 | 历史规则的源时区，不能用当前店铺位置替代 | 否 |
| `pricing_releases.time_zone` | 新发布固定 UTC，仓储和运行器仍读取 | 为未声明时区的历史方案固定当时的业务时区 | 否；是实际 SQL 列 |
| `app_settings['venue.operations'].timeZone` | 已废弃的业务设置，升级时归一为 UTC | 未绑定发布的旧规则、0028 首次回填发布的优先默认来源 | 旧数据转换前不能清除；新业务无需依赖它 |
| `app_settings['store.profile'].timeZone` | 店铺位置对应的展示／编辑时区 | 旧规则缺少其他来源时的默认来源 | 保留展示功能，且必须在旧规则转换之后再按位置补齐 |
| 账单／历史 metadata 的 `pricingExplanation.timeZone` | 新解释为 UTC，UI 从时间点重新格式化 | 换算旧 `ruleTimeRange` 说明中的裸时钟 | 转换前保留；仅删标签不会转换时钟 |
| API `shop.timeZone`、预览 `timeZone`、Swift `Shop.timeZone` | 店铺 UI 与规则展示的 IANA 时区 | 与规则业务标签是不同概念 | 保留 |

固定收费 `charge.fixed` 没有每日规则，不需要添加方案时区。

## 完整写入、执行与客户端链路

- **React 规则编辑器**：`ui/merchant/Pricing.tsx` 和 `pricing-clock.ts` 将 UTC 规则投影到店铺时区，编辑／预览提交前转换回 UTC。方案时区缺省时读取为 UTC。清除业务标签不能清除这些 UI 转换。
- **API / application**：`staff-pricing.ts` 的 `withUtcPricingClock` / `withUtcCapClock` 将显式源时区转换到 UTC。缺省即 UTC，不读取店铺时区推断输入含义。仅有 UTC 标签不会自动将当地时钟转换成 UTC。
- **仓储、设置向导与初始化**：`serializePricingProviderConfig` 对未声明时区的计时／封顶规则默认 UTC，不移动任何时钟；显式源时区保持原值。旧库转换器直接解析原始 JSON，不经新序列化器，因而不会先把隐式旧规则错误标成 UTC。
- **SQL 发布与会话**：0028 为旧状态建立版本、发布和会话绑定，发布保留旧业务时区；0029 将之后的新发布改为 UTC。`repositories.findRelease` 查询 `time_zone` 并返回它。SQLite bootstrap 同样包含这套结构和发布 SQL。
- **收费、入场与封顶**：runtime 优先使用 `provider.timeZone`，缺省使用已固定的发布时区；core 的时段、日期匹配、封顶锚点仍接受这些时区参数。平台的 Live Activity、麻将入场检查也读取方案／发布时区。数据迁移完成后这些值为 UTC，当前代码仍有依赖。
- **优惠日期与日限额**：`asset-definition-effects.ts` / `settlement-service.ts` 已明确使用 UTC，与方案的时区属性无关。此次字段退役判断不等于把优惠日历改回店铺时区。
- **事件 API、账单 Web UI**：API 仅在响应边界格式化事件时间点；规则 provider、裸时钟和计费解释不会被递归投影。商户账单按店铺时区、玩家账单按设备时区展示。带偏移的 ISO 时间保持同一时间点。
- **Swift（`hinata_go/ios/PrismClip`）**：模型中的 provider 时区是可选字段，规则组件缺省 UTC，再投影到 `shop.timeZone`；账单事件使用手机时区。这两个读取点允许未来省略 provider 标签，仍需保留店铺展示时区。
- **Koishi 子模块**：`display-time.ts` 解析 API 时间点并使用响应携带的偏移展示，不读取计费 provider 或发布的业务时区。删除计费业务字段不会直接影响机器人时间显示；API 事件偏移仍须保留。
- **部署保护**：`deployment-gate.ts` 的永久写入触发器要求新 provider 标签明确为 UTC，用来阻止旧 Worker 迟到写入。`deployment-control.ts` 同时检查当前方案、历史版本和发布时区。只删属性会触发写入错误／健康检查失败，只 DROP 列会使查询和发布 SQL 失败。

## 旧 PRiSM 数据库升级

`migrateLegacyPricingToUtc` 的转换依据：

| 转换对象 | 源时区选择顺序 |
| --- | --- |
| 被发布引用的历史版本 | 方案显式 `timeZone` → 当次发布 `time_zone` |
| 未被发布引用的历史版本 | 方案显式 `timeZone` → `venue.operations` → `store.profile` → UTC |
| 当前配置 | 方案显式 `timeZone` → 当前发布 `time_zone` → `venue.operations` → `store.profile` → UTC |
| 账单解释中的裸区间 | 解释自己的时区与实际收费日期 |

同样的 `10:00–次日 03:00`，上海来源转换为 UTC `02:00–19:00`，东京来源转换为 `01:00–18:00`，原本已经是 UTC 的来源则维持 `10:00–03:00`。因此不能先把旧标签统一改成 UTC，再运行时钟转换。

如果同一隐式版本被上海、东京的发布共享，迁移为各时区生成对应版本，保留历史计费身份、发布 ID 和会话绑定。若没有 0028 版本表，0028 先根据仍保留的旧设置回填发布，再运行 UTC 数据转换。这只能保留升级时数据库实际存在的状态，不能恢复旧系统未保存的历史规则版本或历史时区。

迁移同时处理当前规则、历史版本和账单解释；日期／星期随跨日转换，季节性历史规则按实际日期展开，保留夏令时 23／25 小时窗口及封顶锚点。已结账金额、余额账本和累计已付金额不重新结算。

`utc-pricing-data-v1` 完成标记和全部转换在同一事务／D1 batch 提交；失败回滚，重复执行跳过，不再次偏移。该标记证明当次迁移成功，不替后来外部导入的旧规则补充缺失的源时区。

`deploy:beta` 当前顺序为：维护入口 → 数据库写入屏障 → Time Travel 检查点 → 全部 SQL → verify Worker → UTC 数据转换 → 店铺位置时区补齐 → 写入约束／健康校验 → 恢复请求。新增 DROP SQL 会在数据转换之前执行，因此不能通过简单新增一个 DROP 迁移退役字段。

## 独立的 prism-neo 导入缺口

`packages/migration` 的 Neo JSON 快照没有规则源时区；`toPricingConfigs` / `toPricingRule` 原样复制 `timeRange`、星期与日期，导入规则默认停用。新版序列化器将未声明的规则保存为 UTC，新发布也是 UTC；之后的 UTC 迁移无法猜出丢失的来源。

已用内存库实际导入一个 `10:00–03:00` 样例，再运行 UTC 迁移：得到 `enabled=0`、`timeZone='UTC'`、区间仍为 `10:00–03:00`。若原规则是上海时间，正确区间应为 `02:00–19:00`。这是独立导入链路缺少来源的问题，保留当前目标库字段本身不能解决；需要从旧部署取得规则源时区，在导入边界明确转换。此次未擅自假定所有 Neo 部署都使用上海时间，也未改变其历史金额。

后台网页导入（`prism-neo-convert.ts`）已补齐来源：以导入目标店铺的时区作为规则源时区，经 `migrateCurrentPricingRules` 换算为 UTC 后直接启用，并设为默认资源组的方案。命令行导入仍缺少来源，规则默认停用，导入文档要求店主验收并手动启用；在其来源转换补齐前，不应将“已标 UTC”当成“已正确换算”。Neo 导入属于另一条路径，不影响现有 PRiSM stable 数据库保留源时区后的升级链路。

## 退役字段需要同步调整的工作

1. 在写入屏障内先完成旧库 UTC 转换与校验，确认不会丢失方案、发布和账单说明的原时区。
2. 让日常运行器、仓储、Live Activity 和计费计算固定使用 UTC；保留旧库转换所需的兼容读取，或使用明确的分阶段升级路径。
3. 协调 D1 SQL 顺序、SQLite bootstrap、版本／发布触发器及历史表保护，不能让 DROP 先于旧数据转换执行。
4. 替换依赖标签的旧 Worker 写入保护与部署校验，再清除 provider JSON 属性及发布列。
5. 同步 API 契约与客户端规则读取，继续保留店铺展示时区和事件偏移；Neo 导入另外补齐源时区转换。

因此可以消除新调用点的 UTC 手填要求；彻底删存储字段属于一次完整的兼容升级，不是本次向导修复所需步骤。
