# 卡片、占用与查人

这份文档说明三件互相关联的事：玩家的卡片怎么保存、怎么知道谁在用哪个资源（占用），以及「店里有谁」怎么列出来（查人）。闲置自动关机和麻将等位也建立在占用之上。

## 1. 卡片

卡号在游戏里等同于登录凭据，所以店铺拿不到明文卡号，也无法从平台层面用卡号查出是哪位玩家。

- **玩家账号里的卡片**：`cards` 表，属于玩家的 PRiSM 账号（MuNET 同步、手动添加、在读卡器上添加）。
- **玩家在某家店的卡片**：`player_cards` 表（迁移 `0041`）。每张卡只存两样东西：
  - 带密钥的哈希 `card_hash`：HMAC，输入是 `店铺 ID:卡号`，密钥由平台的 `URL_ENCRYPTION_KEY` 派生。用于认出机台回报的卡，同一张卡在不同店铺的哈希不同。
  - 加密的卡号 `card_encrypted`：AES-GCM，用于替玩家把卡发给机台。

  两者都依赖平台密钥，店铺的数据和备份都不能把卡号对应到玩家。一位玩家可以有多张卡；同一家店里一张卡只属于一位玩家，已属于别人的卡不会被改绑（`taken`）。
- **什么时候存进店铺**：只有两种情况。
  1. 玩家在这家店的扫码页用账号里的卡刷卡（`POST /api/v1/machines/login` 成功后）。
  2. 玩家在这家店的读卡器上添加卡片（见下文）。
- **发卡给机台**：店员替玩家刷卡（`playerId`）或 Bot 替玩家刷卡时，取这位玩家在本店最近用过的卡，解密后只交给执行器。Bot 请求里指明了卡号（`subject`）时，只有这张卡确实属于该玩家才会使用。
- **旧数据**：以前以明文存在 `player_identities`（provider `aime`）里的卡，第一次用到时移入 `player_cards`，并删除明文行。店铺备份不再导出 `aime` 身份，也不包含 `player_cards`；恢复后玩家再次刷卡时会重新绑定。
- **设备日志**：IO 回报的卡片事件不再保存卡号，只保留卡类型、读卡口和来源，并在事件的 `player_id` 上记下卡主人。迁移 `0041` 清除了已存事件里的卡号。

代码：`packages/server/src/resources/cards.ts`。

### 在读卡器上添加卡片

扫码页「选择卡片」右侧的加号（只在直连平台的 HINATA IO 机台上出现，`machine.cardCapture`）：

1. `POST /api/v1/devices/session/cards/capture`，请求带 `{ticket, location?}`，打开 60 秒的添加窗口。机台不在线时返回 `DEVICE_UNAVAILABLE`。
2. 页面只显示「请把卡片放在「机台名」的读卡器上」和取消按钮，卡片列表和投币暂时隐藏；页面轮询 `GET /api/v1/devices/session/cards/capture/:id?ticket=`。
3. 窗口内读卡器报来的第一张卡（不含平台自己下发的卡）会加入玩家账号（`cards`，来源 `reader`），同时绑定到本店（`player_cards`，来源 `reader`）。

结果有以下几种：

| 结果 | 含义 |
| --- | --- |
| `added` | 账号里原来没有这张卡，已加入账号并绑定到本店 |
| `bound` | 账号里已有，这次绑定到本店 |
| `exists` | 已经绑定在本店 |
| `taken` | 已绑定到本店的其他玩家，不做任何改动 |
| `unsupported` | 没有游戏可用卡号的卡，例如只有 FeliCa ID 的卡 |
| `expired` | 窗口内没有读到卡 |

结果只返回给打开窗口的那个账号，并且只读一次。代码：`resources/card-capture.ts`，以及中继对象 `durable-objects/machine-relay.ts` 里的 `startCardCapture` / `cardCaptureResult`。

## 2. 占用

**占用**表示有人正在用某个资源。每个资源有两个参数（迁移 `0042`，`machines` 表）：

| 参数 | 含义 |
| --- | --- |
| `capacity` 容量 | 能同时用的人数。0 表示不会被占用，例如空调、门锁、Bot；柜机通常是 1，两人共用一个入口的游戏是 2。新建资源时有 HINATA IO 的默认 1，其余默认 0。麻将桌的容量就是开桌人数（2–8），麻将能力不再单独设置人数；有人在座时不能修改（`MAHJONG_IN_USE`）。迁移 `0042` 把原来麻将能力配置里的人数搬到了容量上。 |
| `occupancy_minutes` 占用时长 | 最后一次看到这个人之后，还算他在用多久，店家按游戏时长设置，默认 15 分钟。决定占用的能力自己掌握占用者时（麻将桌的座位）不适用，见下文。 |

每段占用是 `resource_occupancies` 的一行，记录资源、玩家、来源、开始时间、最后一次看到的时间、到期时间、结束时间和结束原因。结束原因有四种：`timeout` 超时、`replaced` 被替换、`left` 离开、`billing_ended` 计费结束。到期时间已过而结束时间还没写的行，按到期时间算作超时结束，下次读写这个资源时补写。

### 谁说了算

每种能力自己判断它的事件意味着什么（`resources/capabilities/*-occupancy.ts`）。一个资源上同时有多种能力时，只听权威度最高的那一种（`resources/occupancy/providers.ts`）：

| 能力 | 权威度 | 怎么判断 |
| --- | --- | --- |
| 麻将桌 `mahjong` | 100 | 座位就是占用，没有超时。座位跟着它当前所在的 session：等位时是麻将桌自己的方案（等位方案），开局后是麻将方案；这条 session 结束时座位就没了 |
| （以后）游戏服务器登录登出 | 介于两者之间 | 登录即开始、登出即结束，不靠超时 |
| HINATA IO `hinata_io` | 10 | 见下表 |

HINATA IO 的判断：

| 事件 | 结论 |
| --- | --- |
| 游戏取走了卡（`card.consumed`） | 卡主人开始占用。机台上直接刷的实体卡和平台下发的卡都算；本店认不出主人的卡不产生占用，资源仍是空闲 |
| 经平台为某位玩家投币或刷卡 | 这位玩家开始占用。外部中继不回报任何事件，只能这样判断 |
| 开机、延迟关机、店员不指定玩家的操作 | 不算占用 |

认不出主人的卡不在任何地方出现：没有「未知玩家」，占用记录、查人和资源卡片都不显示它。同一个人之后经平台投币或刷卡时，就会以他的身份开始占用。

读卡器灯光不参与判断。更复杂的推断（比如按灯光变化推测一局是否结束）只需要改 HINATA IO 自己的判断模块。

### 占用时长什么时候不适用

占用时长只用于从事件推断出来的占用：看不到人离开，只能按「多久没动静」判断。决定占用的能力自己掌握占用者时（提供 `held()` 的能力，目前是麻将桌的座位），入座开始、下桌结束，占用时长不适用：

- 占用本身没有到期时间；
- 闲置判定里，经平台的开机、延迟关机等操作不再让设备忙一段占用时长，只看座位（`shop-hub-idle.ts` 把这类资源的占用时长当作 0）；
- 资源编辑页的「占用时长」显示为「不适用」，下方写明原因。

这条规则由能力是否提供 `held()` 决定，不针对麻将单独判断；以后的游戏服务器登录登出也会照此处理。

### 规则

规则对所有来源都一样（`resources/occupancy/rules.ts`）：

- 已经在占用的人又出现了：延长他的占用。
- 新来的人：开始占用。资源已满时，替换掉开始得最早的人，结束原因为「被替换」。
- 超过占用时长没有新动静：按超时结束，结束时间就是到期那一刻。

读卡口编号不参与判断，因为游戏不使用 IO 的读卡口。

### 闲置自动关机

闲置和占用是同一件事。一台设备在以下情况都算忙，不会被自动关机：

- 有人占用它（按占用时长到期为止，座位则一直算忙）；
- 在它的占用时长内，有人经平台开机、延迟关机或发起操作。

设备从不忙的那一刻起，再经过店铺设置里的**闲置判定时长**（`device.minutes`，默认 10 分钟）才算闲置：

```text
空闲时刻 = max(最后一次操作 + 占用时长, 占用到期时刻)    # 座位类资源的占用时长按 0 计
闲置时刻 = 空闲时刻 + 闲置判定时长
```

所以自动关机触发时，机器上一定没有人，也不需要再刷新占用。店铺设置「位置与设备 → 闲置自动关机」里只有三项：是否启用「设备闲置自动处理」、闲置判定时长，以及店里有人时怎么处理闲置设备（只标记、Bot 提醒、直接关机）。旧设置里的 `device.defaultMinutes` 读取时转成闲置判定时长。代码：`resources/capabilities/idle-power.ts`、`durable-objects/shop-hub-idle.ts`。

## 3. 麻将等位

麻将桌资源自己的方案（专属方案，或所在资源组的方案）就是**等位方案**，麻将能力里设置的方案是**对局方案**：

- 上桌需要等位方案在计费中：玩家在麻将桌页面确认，或店员、Bot 替玩家上桌时直接开始。
- 满桌时，为桌上每个人开始对局方案。店家可以按需配置关系，例如：
  - 等位免费：等位方案设为免费方案，并让它与对局方案互斥。开局时等位方案自动结束。
  - 对局依赖基础方案：开局时基础方案自动开始；原来就在计费的（比如边等边玩音游的人）保持不变。
- **下桌**只结束座位当前所在的那条 session：
  - 已开局时结束对局方案。
  - 还在等位时结束等位方案，但只在等位方案是为这张桌子开始的（`session.metadata.resourceId` 是这张桌子），并且没有其他在计费的方案依赖它时才结束。
  - 随之开始的基础方案继续计费，离店就是结账。

  下桌的响应带 `billing.remaining`，Bot 会回复「仍在计费：…」。
- 已开局的桌上，等位方案可能已经结束，但占着座位就算在使用这张桌子：扫码页直接显示座位，不再要求确认（`occupancy.holds`）。按事件推断出来的占用不享受这一点，否则计费已经被停掉的人还能凭占用继续使用资源。

## 4. 查人

在店的人包括：有任意进行中 session 的玩家，以及正在占用资源的玩家。每个人只列一次，列在他**最具体的位置**（`resources/roster.ts`）：

1. 他正在占用的资源，显示「人数/容量」。同时出现在两个资源上（换机器时前一个还没超时）的，列在最后一次看到他的那个资源。
2. 没有占用任何资源的，列在他最具体的方案下：在他正在计费的方案里，选没有被其他方案依赖的那个；有多个时取开始最晚的，再按方案名排序。没有计时方案的店铺的占位 session 显示为「计费」。Koishi 插件的 `list`（不带名称）不按方案分：没有占用资源的人统一列在「其他」下；网页「在店」页仍按方案分组。

只剩未结账单的玩家不算在店。网页「在店」页仍然列出他们以便结账，并单独显示「待结账」人数。

接口：

| 接口 | 说明 |
| --- | --- |
| `GET /rpc/staff/roster`、`GET /rpc/integration/roster` | `{total, groups}`。每组有 `kind`（`resource` 或 `plan`）、`id`、`name`、`members`，资源组另有 `capacity`。带 `?name=` 时按资源名、别名或方案名只列一项：资源列出上面的所有人，方案列出所有在计费这个方案的人；找不到返回 404 `ROSTER_TARGET_NOT_FOUND` |
| `POST /rpc/integration/players/by-identity/presence` | 一位玩家：`{inShop, plans, occupying}` |
| `GET /rpc/staff/live-players` | 额外带 `roster`，网页「在店」页的「按位置分组」使用它 |
| `GET /api/v1/merchant/machines/occupancy?shopId=` | 每个可占用资源当前的占用者、人数和容量；资源页的卡片显示这些，点玩家名打开他在「在店」页的详情和账单（`/merchant/:shop/live?player=`）。另带 `powerOffAt`：正在闲置倒计时的设备何时自动关机，卡片上显示为「HH:MM 自动关机（N 分钟后）」，见 [集成与设备](integrations-and-machines.md#闲置自动关机) |
| `GET /api/v1/merchant/machines/:id/occupancy` | 一个资源的占用记录，最新的在前，可带 `limit`、`before`；资源卡片「操作记录」里与设备操作记录一起显示 |

Bot 的 `list` 直接按 `roster` 输出，`list <资源或方案>` 只列这一项。
