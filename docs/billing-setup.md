# 已有店铺转换为计费店铺

店铺负责人打开 React 商户工作台的「设置」，在「营业与计费」分类点击「转换为计费店铺」。此入口只在店铺未启用计费、且尚未备齐有效余额资产和默认计费方案时显示，manager/viewer 不能执行转换。此时分组里只有向导，不显示「启用入场计费」开关和保存按钮——配置不全时手动启用必然被拒（`BILLING_CONFIGURATION_REQUIRED`）。配置就绪（例如导入数据后）或计费已启用时，才显示「启用入场计费」「启用前台收银」；默认计费方案是默认资源组的方案，在「资源」页默认资源组的「编辑」里修改；「启用入场计费」是独立开关，配置完成不自动开启。

1. 填写充值余额和赠送余额的名称、每小时单价、宽限分钟与全天封顶金额。金额以元为单位，封顶填 `0` 表示不封顶。
2. 可勾选「同时启用前台收银」；默认不勾选，转换后也可以在设置中单独打开。
3. 核对收费标准，点击「确认转换并启用计费」。系统补齐基础余额资产、创建全天「标准入场」计费方案并设为店铺默认计费方案，同时启用计费。完成后工作台立即显示在店、玩家、计费、资产和记录页面。

转换保留店铺编号、设备、玩家、资产数量、历史记录和已有计费方案；已有 `currency/paid`、`currency/free` 资产直接复用，其名称不会被覆盖。新的标准入场方案成为默认计费方案，旧方案仍可在「计费」中管理。店铺原有位置校验、平台身份自动注册开关及联系信息也会保留。若基础余额资产已归档，先在「资产」页面恢复，再执行转换。向导和新店初始化创建的全天方案由统一存储序列化方法自动补齐 UTC 标记，调用方无须手动填写；兼容部署时安装的 UTC 写入约束。

不需要创建 Bot 凭据，也不需要连接 Bot 才能启用计费。需要 Bot 时，负责人在「资源」页添加带「店铺 Bot」能力的资源，保存时签发凭据。新建计费店铺的「同时创建 Bot 接入凭据」默认不勾选，仅主动勾选才创建凭据，并显示可复制的接入凭据、店铺编号和 API 地址（与设置页同一口径）。新建店铺向导第一步是三选一的经营方式：自助计费（无前台）、前台收银、不使用计费；选前台收银会同时开启前台收银。新店铺默认要求绑定平台身份并自动建档，身份策略由[开店指引](merchant-setup-guide.md)引导店长确认。

计费页的「计费是怎么算的」按钮打开计费图解（单位与宽限、跨时段与封顶、多条计费与消费封顶、结账扣款顺序），与开店指引共用。

计费页的规则列表给默认计费方案加「默认」标记，并链接到「资源」页：新建的规则要被资源组、设备或其他规则的「依赖」引用才会计费，见 [资源与资源组](resources.md)。

手动启用计费仍可使用原有「启用入场计费」开关，但须有有效余额资产并设好有效的默认计费方案；这些条件不包含 Bot 凭据。前台收银仅保存计时档案、不为玩家保存资产，店铺的基础资产定义不代表卡片档案有预存余额。详见 [前台收银](cashier.md)。

默认计费方案只能是一个未归档的按时计费方案（设置接口的 `entryPricingIds` 最多一项）。原来选中的方案如果停用或归档，设置页面会标为不可用。保存被拒绝时区分「余额资产缺失」「未设置默认计费方案」「默认方案失效」。

## 「计费」页的规则编辑器

规则列表新增「时段」列（按时计费显示时段数量，固定收费显示「单次收取」）。规则编辑器是宽幅弹窗：上半是**基本信息**（名称、计费方式、启用），下半按两栏布局——**左侧常驻 24 小时预览环**，右侧是**计费时段**列表。点击环上的某个时段会直接展开右侧对应卡片，因为环本身不动，不需要在弹窗里上下跳。每个时段是一张默认折叠的卡片，标题行显示「名称 · 开始–结束 · 单价/分钟」，点开才渲染输入框。保存按钮吸底常驻。

时段名称为空、消费封顶的封顶金额不大于 0、每隔分钟数不大于 0 时（按时计费的时段封顶填 0 表示不封顶，玩家扫码页也不再显示它），保存会被拦下并自动展开对应时段，把光标带到需要修改的位置——浏览器无法聚焦折叠区域里的必填项，所以校验在前端完成（表单使用 `noValidate`）。

## 平台接口

`POST /api/v1/shops/:shopCode/billing/setup`，需要商户会话及店铺 owner 权限：

```json
{
  "paidName": "余额",
  "freeName": "赠送余额",
  "hourlyPrice": 12,
  "graceMinutes": 5,
  "dailyCap": 60,
  "cashierEnabled": false,
  "operationId": "00000000-0000-4000-8000-000000000001"
}
```

`cashierEnabled` 可省略，默认 `false`。响应使用标准 `data` 包裹，包含已保存的店铺计费设置及 `pricingConfigId`。配置和操作成功响应记录在同一 D1 事务中提交；设置更新、转换和前台操作共用店铺操作锁。失败整批回滚，可使用相同 UUID 重试；锁竞争不会提前留下 pending 操作。旧版本在首次 500 后留下的 unknown/pending 转换记录，在参数匹配且店铺仍未启用计费时也能重试。相同 UUID 和请求参数可重放成功响应，不会重复创建配置；不同 UUID 对已启用计费的店铺再次转换返回 `409 BILLING_ALREADY_ENABLED`。归档基础资产返回 `409 BILLING_ASSETS_ARCHIVED`，请求编号被用于不同参数返回 `409 OPERATION_CONFLICT`。此恢复逻辑仅用于店铺计费转换，不修改扣款、结账和设备操作的重试规则。

店铺负责人读取或保存 `GET/PUT /api/v1/shops/:shopCode/settings` 时，响应增加只读字段 `billingConfiguration`：

```json
{
  "ready": true,
  "balanceAssetsReady": true,
  "entryPricingReady": true,
  "invalidEntryPricingIds": []
}
```

`ready` 表示有效余额资产存在、默认计费方案有效，独立于 `billingEnabled`。已有计费店铺的资产或默认计费方案失效时，仍可单独修改位置校验、身份绑定等设置；不会因此自动关闭计费。启用计费、启用前台收银或更改默认计费方案时，配置校验失败仍返回 `409 BILLING_CONFIGURATION_REQUIRED`，`error.details` 带相同结构，指出未完成的部分和失效方案编号。`time.cap` 不能作为默认计费方案；它覆盖所有按时计费的方案，不再选择适用方案（旧数据里保存的选择在下次保存时清空）；也不会因当前时刻落在非营业区间就要求重新初始化。

`POST /api/v1/merchant/shops` 的 `billingSetup.createBotToken` 默认 `false`，未主动选择时不创建集成凭据，响应 `botToken: null`；显式 `true` 时创建凭据并仅在该响应返回明文 token。

验证：`bun test packages/platform/test/billing-setup.test.ts --timeout 60000`、`bun run typecheck`、`bun run build:web`。平台集成测试使用真实 Miniflare D1，覆盖无 Bot 启用、数据保留、权限、重放、前台收款和事务回滚。
